# 实现计划：基于文件夹的 Hub/MOC 初始化与长期维护

## 一、目标概述

建立一个“先生成建议、人工审核、批准后写入”的 Hub/MOC 管理流程。

当前实现采用已批准的 10 个第一层文件夹白名单：`计算机`、`项目`、`AI学习图谱`、`编程`、`AI-Knowledge-Base`、`modern_genai_bilibili-main`、`摄影与器材`、`阅读`、`python`、`VUE3笔记`。子文件夹只在对应顶层 MOC 内分组，不生成独立 MOC。

系统根据白名单第一层文件夹，为每个有 Markdown 笔记的白名单文件夹生成一个候选 `MOC - 文件夹名称.md`。Hub 的归属只根据第一层文件夹确定，不使用 embedding 分类。

Vault 根目录下直接存在的 Markdown 笔记不生成 `MOC - 根目录.md`，也不自动归入虚拟 Hub。这类笔记会在审核报告中作为“根目录未归类笔记”单独列出。

候选 MOC 首先生成到 Vault 外部的审核目录。只有在用户审核并批准后，系统才可以写入真实 Vault。

## 二、已确定的架构规则

- 文件夹层级是 Hub 和 Parent 关系的唯一分类依据。
- 每个有 Markdown 笔记的白名单第一层文件夹生成一个候选 MOC。
- 白名单内的子文件夹只作为 MOC 内部的分组，不生成独立 MOC。
- 非白名单第一层文件夹不生成 MOC，也不自动归入其他 Hub。
- Vault 根目录下的直接笔记不生成 MOC，也不自动分配到虚拟 Hub。
- MOC 文件名统一为 `MOC - 文件夹名称.md`。
- MOC Frontmatter 使用 `knowledge_role: hub` 声明 Hub。
- `knowledge_parent` 保存父级 MOC 的 Wikilink。
- `hub_source_folder` 保存该 MOC 对应的文件夹路径。
- `hub_generated: true` 标记该 MOC 由系统生成。
- 正文只保留空白的 `# 导语`。
- 系统生成的关系放在 `AUAKA:BEGIN GENERATED RELATIONS` 和 `AUAKA:END GENERATED RELATIONS` 标记之间。
- 标记区域以外的用户内容不得被覆盖。
- 普通笔记之间已有的 Wikilink 继续保留，但不改变文件夹产生的 Hub 归属。
- embedding 只用于语义检索、RAG 和语义可视化，不参与 Hub 分类。
- 每次扫描都生成确定性的候选结果、差异报告和审核记录。

## 三、处理流程

```text
扫描 Vault 文件夹和 Markdown 文件
        ↓
生成候选 Hub 树
        ↓
生成 MOC 草案
        ↓
生成审核报告和变更清单
        ↓
用户审核与批准
        ↓
安全写入 Vault
        ↓
建立增量维护注册表
        ↓
重新生成 Artifact v2
```

## 四、任务拆解

### 阶段一：基础数据结构

#### Task 1：定义候选方案与审批契约（已完成）

**目标：** 为候选 Hub、父子关系、关系变更、冲突和审批决定建立版本化数据结构。

**验收标准：**

- [x] 记录源文件夹、MOC 路径、父 MOC、子笔记、子 Hub 和稳定 ID。
- [x] 每个变更都有明确动作：`create`、`update-generated-region`、`move`、`stale` 或 `conflict`。
- [x] 每个变更都有审批状态。
- [x] 拒绝路径穿越、重复 MOC 路径、重复 Note ID 和父级循环。

**验证方式：** 模型序列化测试、非法输入测试和契约版本测试。

**依赖：** 无。

**预计范围：** 中等。

#### Task 2：建立确定性的文件夹到 Hub 索引（已完成）

**目标：** 只根据 Vault 文件夹结构生成候选 Hub，并将普通笔记归入最近的父文件夹 Hub。

**验收标准：**

- [x] 每个包含 Markdown 笔记的非根目录文件夹恰好生成一个候选 MOC。
- [x] 父 MOC 是最近的、同样存在候选 MOC 的父文件夹。
- [x] Vault 根目录下的直接笔记不生成 MOC，不归入虚拟 Hub。
- [x] 文件夹为空时不生成 MOC。
- [x] 输入文件顺序不影响输出。
- [x] 路径分隔符、大小写冲突和 Unicode 文件夹名称有明确处理规则。
- [x] 该模块不调用 embedding 或语义相似度计算。

**验证方式：** 使用嵌套目录、空目录、根目录笔记、Unicode 名称和乱序输入建立测试夹具。

**依赖：** Task 1。

**预计范围：** 中等。

### 检查点 A：候选结构基础（已完成）

- [x] Task 1 和 Task 2 测试通过。

### 阶段二：MOC 草案与审核报告

#### Task 3：生成候选 MOC 草案（已完成）

**目标：** 生成统一格式的 `MOC - 文件夹名称.md` 草案。

**验收标准：**

- [x] MOC 文件名稳定、可预测且不会产生路径穿越。
- [x] Frontmatter 包含 Hub 角色、父 MOC、源文件夹和生成器版本。
- [x] 正文包含空白的 `# 导语`。
- [x] 子 Hub 排在普通笔记之前。
- [x] 生成关系使用固定的 AUAKA 起止标记。
- [x] 生成内容按稳定顺序排序。
- [x] 同一输入重复生成时内容完全一致。

**MOC 示例：**

```markdown
---
knowledge_role: hub
knowledge_parent: "[[MOC - 计算机视觉]]"
hub_source_folder: "计算机视觉/目标检测"
hub_generated: true
hub_generator_version: "1.0"
---

# 导语

<!-- AUAKA:BEGIN GENERATED RELATIONS -->
## 子主题

- [[MOC - 两阶段检测]]

## 笔记

- [[YOLO]]
- [[两阶段检测]]
<!-- AUAKA:END GENERATED RELATIONS -->
```

**验证方式：** Markdown 黄金文件测试和重复渲染字节一致性测试。

**依赖：** Task 2。

**预计范围：** 中等。

#### Task 4：生成审核报告和差异清单（已完成）

**目标：** 将候选结构与已批准的关系注册表进行比较，生成可读的审核报告和机器可读的 JSON 清单。

**验收标准：**

- [x] 报告列出新增、生成区域更新、移动、过期、冲突和未解析链接。
- [x] 报告单独列出 Vault 根目录下未归类的直接笔记。
- [x] 手动内容只标记为“保留”，不能被静默删除。
- [x] 报告包含候选 Hub 数量、笔记归属数量、冲突数量和 Vault Hash。
- [x] 同一输入重复生成时，报告的语义内容保持一致。
- [x] 用户可以逐项批准或拒绝候选变更。

**验证方式：** 首次运行、无变化、笔记移动、笔记删除、MOC 手动编辑和路径冲突测试。

**依赖：** Task 3。

**预计范围：** 中等。

### 检查点 B：人工审核门禁（等待审核真实候选结果）

- [x] 不接触真实 Vault 的 dry-run 可以完整生成草案和报告。
- [ ] 用户审核真实 Vault 的候选 MOC 结构。
- [x] 未经用户批准，Task 5 不得执行写入。

### 阶段三：批准写入与长期维护

#### Task 5：实现显式审批和安全写入 Vault

**目标：** 只将用户批准的候选 MOC 和关系变更写入真实 Vault。

**验收标准：**

- [ ] 没有审批文件或明确审批参数时，不执行写入。
- [ ] 新 MOC 只在对应文件夹中创建。
- [ ] 已存在的 MOC 只更新生成关系区域。
- [ ] `AUAKA` 标记缺失时生成冲突，不执行破坏性替换。
- [ ] 原有 Frontmatter、导语和手动正文保持不变。
- [ ] 写入使用临时文件和原子替换，并保留可恢复副本。
- [ ] 写入后重新扫描并核对文件路径和内容 Hash。

**验证方式：** 临时 Vault 集成测试、写入中断恢复测试、手动编辑保护测试和 Git 暂存区审计。

**依赖：** Task 4，且必须通过检查点 B。

**预计范围：** 较大，若超过一个实现周期需要继续拆分。

#### Task 6：建立增量维护与关系注册表

**目标：** 记录已经批准的 Hub 关系，只对 Vault 后续发生的变化生成增量建议。

**验收标准：**

- [ ] 注册表记录 Vault Hash、生成器版本、源文件夹、MOC 路径和已批准关系。
- [ ] 新增、移动、重命名和删除笔记都能生成稳定的变更建议。
- [ ] 尽可能根据稳定 Note ID 识别重命名。
- [ ] 无法确定的重命名必须进入冲突列表。
- [ ] 失效 MOC 只建议归档或删除，不自动删除。
- [ ] 全量重建与增量维护最终生成相同的批准关系图。

**验证方式：** 多步骤 Vault 变更测试，以及全量构建与增量构建结果一致性测试。

**依赖：** Task 5。

**预计范围：** 中等。

### 阶段四：接入 Artifact v2

#### Task 7：将批准后的 Hub 关系接入 Artifact v2

**目标：** 将已经批准的 MOC 和父子关系纳入现有知识空间，同时保持真实数据私有。

**验收标准：**

- [ ] 批准后的 MOC 成为显式 Hub 节点。
- [ ] Hub 具有确定性的 parent、depth 和 topic root。
- [ ] 文件夹产生的关系与普通 Wikilink 关系可以区分。
- [ ] Artifact 元数据记录 Hub 注册表 Hash 和生成器版本。
- [ ] Hub 分类不调用 embedding。
- [ ] Semantic、Galaxy 和 Compact 三套坐标契约保持有效。
- [ ] 真实 Artifact 只保存在本地，不进入 Git。

**验证方式：** Artifact 夹具测试、真实 Vault 私有 dry-run 和浏览器预览测试。

**依赖：** Task 6。

**预计范围：** 中等。

## 五、主要风险与应对

| 风险 | 影响 | 应对方式 |
|---|---|---|
| 文件夹名称导致 MOC 路径冲突 | 高 | 规范化、校验并进入人工冲突审核 |
| 已有 MOC 包含手动修改 | 高 | 只更新生成区域，缺少标记时要求人工处理 |
| 批量写入损坏 Vault | 高 | dry-run、审批文件、原子写入、备份和写后审计 |
| 文件夹结构过于扁平或杂乱 | 中 | 先审核候选结构，可逐项拒绝 |
| 文件重命名导致关系断裂 | 中 | 使用稳定 Note ID，无法确认时进入冲突列表 |
| 生成 MOC 后 Artifact 节点数量增加 | 中 | 先生成本地私有 Artifact，审核后再纳入正式预览 |

## 六、执行顺序

```text
Task 1 → Task 2 → 检查点 A
                 ↓
Task 3 → Task 4 → 检查点 B（用户审核）
                 ↓
Task 5 → Task 6 → Task 7 → 检查点 C
```

第一轮实现只做到 Task 4：生成真实 Vault 的候选 MOC 和审核报告，不修改 Vault。你审核候选结果后，才进入 Task 5。
